## 3. 같은 내용은 한 곳에만 쓴다 (단일 출처)

같은 사실을 두 곳에 쓰면 **언젠가 한쪽이 틀린 말**이 된다. 그래서 사실마다 **정답이 사는 곳**을 정한다.
나머지는 **링크로 가리킨다.**

| 사실 | 정답이 사는 곳 | 다른 곳에서는 |
|---|---|---|
| 지금 해야 할 일 / 현재 상태 | **C01 §7** | "C01 참조" 링크 |
| 용어 정의 | **C02** | 링크 |
| 요구사항(스토리) | **D04 §2.2** | D05는 **옮겨 적되** 원본은 D04 |
| 태스크 목록 | **D05 §3.1** | D06은 완료%만 추가. **어긋나면 D05가 맞다** |
| 테스트 결과 숫자 | **D07 §6** | C01·D08은 D07 숫자를 인용 |
| 코드 규칙 | **C05** (원본은 저장소 `CLAUDE.md`) | 링크 |
| 결정과 이유 | **C06** | 링크 |
| 기능의 상세 동작 | 저장소 `docs/08-overview.md`, `09-handover.md` | D 문서는 요약 + 링크 |
| 일정 | **D02 §4 / D05 스프린트 구분표** | C01 §8은 요약본 |

> **저장소 기존 문서(`docs/00~12`)와의 관계** — 기존 문서는 *개발 중 쌓인 기술 기록*이고, 이 폴더는 *체계화된 공식 산출물*이다.
> 겹치는 부분은 **이 폴더가 요약·색인**, 기존 문서가 **세부 원본**을 맡는다. 서로 다르면 **기존 `07-next-tasks.md`(진행 상태)와 `CLAUDE.md`(규칙)** 가 코드에 더 가깝다 — 발견 즉시 고친다.

## 4. 이름 규칙

### 4.1 파일 이름

| 대상 | 규칙 | 예 |
|---|---|---|
| D 문서 | `D{두 자리}_{한글이름}.md` (공백 없이 붙임) | `D04_프로덕트백로그.md` |
| C 문서 | `C{두 자리}_{한글이름}.md`, 단어 사이는 `-` | `C04_개발순서와-게이트.md` |
| 폴더 | `{두 자리}_{한글이름}` | `00_개발컨벤션` |
| 스프린트가 여러 번인 문서 | **한 파일 안에서 `[N]차` 절을 추가** (파일을 늘리지 않는다) | D05, D06 |
| 날짜가 들어가는 기록 | `YYYY-MM-DD` | `mentoring-2026-10-10.md` |
| 코드 파일 | [C05 §3](C05_개발규칙.md) | |

### 4.2 문서번호 (제출용)

`20{연도 두 자리}-{팀이름}-Doc-{세 자리}` — D01=001 … D08=008.
예) `2026-TeamName-Doc-004`. 팀 이름이 정해지면 D02 헤더에 한 번만 적는다. `미정`

### 4.3 버전

`주.부` (예 1.0, 1.1, 2.0)

| 변화 | 올리는 자리 | 예 |
|---|---|---|
| 오타·표현 다듬기 | 올리지 않음 (이력도 생략 가능) | |
| 내용 추가·수정 | **부** +1 | 1.0 → 1.1 |
| 구조·범위가 바뀜 (기능 추가·삭제) | **주** +1 | 1.x → 2.0 |
| 초안(검토 전) | 0.x | 0.1 → 0.2 |

> 이 문서 세트는 **프로토타입이므로 모두 0.1** 로 시작한다. 비개발 팀원 검토를 거쳐 문서마다 1.0으로 올린다.

### 4.4 제·개정 이력

D03·D04는 **필수**(양식 요구). 나머지도 같은 형식으로 문서 맨 아래에 둔다.

```
| 버전 | 날짜 | 작성자 | 제/개정사항 | 비고 |
```

## 5. 상태 표기 — 확정 · 후보 · 제안 · 미정

문서에서 **정해진 것과 안 정해진 것을 섞어 쓰지 않기 위한** 네 가지 말. 이 네 말 외의 애매한 표현("아마", "~할 수도 있다")은 쓰지 않는다.

| 표기 | 뜻 | 쓰는 법 | 예 |
|---|---|---|---|
| **확정** | 결정이 끝남 | C06에 결정 기록이 있어야 한다 | "노동자 화면 외부 요청 0건 — 확정" |
| **후보** | 선택지 중 하나 | 후보끼리 비교한 표를 함께 둔다 | "에이전트 A/B/C — 후보" |
| **제안** | 작성자 의견, 팀 검토 전 | 검토되면 확정/폐기로 바꾼다 | "스프린트 3회 구성 — 제안" |
| **미정** | 정해지지 않음/모름 | **누가·언제까지** 를 함께 적는다 | "팀 이름 — 미정 (byeonsoyun, 10/15)" |

## 6. 문체 규칙 (모든 문서 공통)

양식이 요구하는 규칙에 **비전공자 배려**를 더했다.

| # | 규칙 | ❌ 나쁜 예 | ✅ 좋은 예 |
|---|---|---|---|
| 1 | **모호한 표현 금지** | "번역이 틀릴 수도 있다" | "AI 번역은 뜻이 뒤집힐 수 있으므로, 운영자가 승인하기 전에는 교육에 쓰이지 않는다" |
| 2 | **모든 문장에 주어·동사·목적어** | "데이터를 입력받아야 한다" | "담당자가 설비 이름을 입력한다" |
| 3 | **개조식으로 짧게** | 긴 줄글 | "~한다" 로 끊어 쓴다 |
| 4 | **표·그림에 번호** 붙이고 본문에서 인용 | | "표 3 참조" |
| 5 | **약어는 처음 한 번 풀어쓴다** | "HITL 적용" | "사람 승인(HITL, Human-in-the-loop) 적용" |
| 6 | **용어는 C02와 같은 말만** | 같은 것을 "교육/코스/강좌"로 섞어 부름 | C02에 정한 말 하나로 통일 |
| 7 | **숫자에는 출처·측정일** | "테스트 많이 통과" | "자동 테스트 1,619건 통과 (2026-10-10 측정)" |
| 8 | **추측은 추측이라고 표시** | 조사 안 한 시장 규모를 사실처럼 | "시장 규모 — 미정 (출처 검증 후 기재)" |

> **7·8번이 특히 중요하다.** 멘토링에서 *"정리된 수치가 실제인지 환각인지 검증을 명확히"* 라는 요청이 있었다. 출처 없는 숫자는 문서에 쓰지 않는다.

## 8. 문서를 고칠 때의 순서

```
 ① 내용 수정 ──► ② 제·개정 이력 한 줄 ──► ③ 영향받는 문서 확인 ──► ④ C01 상태판 갱신(필요 시)
```

**영향받는 문서 확인표** — 위에서 바뀌면 아래도 확인한다.

| 바뀐 것 | 함께 확인할 문서 |
|---|---|
| 기능이 추가/삭제 | D03 → D04 → D05 → D06 → D07 (사슬을 따라 내려감) |
| 일정 변경 | D02 §4, D05 스프린트 구분표, C01 §8 |
| 결정이 바뀜 | C06에 새 결정 추가(옛 결정은 "대체됨"으로 표시), 영향받는 C·D 문서 |
| 테스트 숫자 변경 | D07 §6, C01 §4.2, D08 |
| 용어 변경 | C02, 그 용어를 쓰는 모든 문서 |

## 9. 점검 체크리스트 (문서를 올리기 전)

- [ ] 빈칸이 없다 (모르면 `미정` + 담당 + 기한)
- [ ] 상태 표기 4종 외의 애매한 표현이 없다
- [ ] 숫자에 출처/측정일이 있다
- [ ] ID가 사슬 규칙을 지킨다 (앞 문서에 없는 ID를 만들지 않았다)
- [ ] 용어가 C02와 같다
- [ ] 제·개정 이력에 한 줄을 남겼다
- [ ] 비개발자 한 명이 읽고 **막히는 곳이 없다**
