# C04 · 개발 순서와 게이트

> **문서 상태** 초안 v0.2 · **최종 수정** 2026-10-22
> **이 문서가 답하는 질문** 개발은 어떤 순서로 하나 · 각 단계가 끝났다는 건 어떤 상태인가 · **지금 우리는 어디에 있나**

---

## 1. 전체 순서 한 장

```
 G0                G1               G2                 G3                G4               G5
 ┌────────┐      ┌────────┐       ┌────────┐        ┌────────┐       ┌────────┐       ┌────────┐
 │ 방향    │ ───► │ 설계    │ ───► │ 스펙    │ ────► │ 상세설계 │ ───► │ 구현    │ ───► │ 검증·   │
 │ 확인    │      │ (무엇)  │      │ (정확히)│        │ (어떻게) │      │ (스프린트)│     │ 인계    │
 └────────┘      └────────┘       └────────┘        └────────┘       └────────┘       └────────┘
  주제·평가표       D01 D03          D04               D06 설계안       D05 → 코드        D07 D08
  공지 확인         사용사례          에픽·스토리        화면/서버/데이터     테스트 → 기록       시연·발표
```

각 단계 끝에 **게이트(통과 조건)** 가 있다. 통과 못 하면 다음 단계로 가지 않는다.
**돌아가는 것은 허용한다.** 구현 중 설계가 틀렸다는 걸 알면 G1~G3로 돌아가 문서를 고친다 ([C03 §8](C03_문서체계와-ID규칙.md)).

## 2. 지금 우리는 어디에 있나

| 단계 | 상태 | 비고 |
|---|---|---|
| **G0 방향 확인** | 🔶 **여기** | 주제 ✅ 아이디어톤 주제 유지 (10/22 확인) · **평가표 공지 대기** ❓. 멘토링 1차 완료(10/10), 2차 창업 10/23, 3차 기술 10/30 예정 |
| G1 설계 | 🔶 병행 | v1.0 기준선 설계는 있음(기존 문서). 해커톤 증분(AI Agent)은 **후보 단계** |
| G2 스펙 | 🔶 초안 | D04 프로토타입 작성 (이번 작업). 후보 에이전트의 스토리는 `후보` 표시 |
| G3 상세 설계 | ⬜ | 서버(`/api`) 구조는 **설계안만** (C06 D-005~D-007 후보) |
| G4 구현 | ⬜ | **평가표 공지 전에는 에이전트 코드를 쓰지 않는다** (확정, D-003) |
| G5 검증·인계 | ⬜ | |

> **현재 단계의 할 일**: G0를 끝내는 데 필요한 정보를 모으고(공지 확인·멘토 의견·수익 모델·출처 검증), 동시에 G1~G3 문서를 **후보 상태로** 준비한다. 비개발 팀원이 할 수 있는 일이 많은 단계다 ([C07](C07_역할과-운영.md)).

## 3. 단계별 상세

### G0. 방향 확인

| 항목 | 내용 |
|---|---|
| 목적 | **무엇을 만들지 결정**하는 데 필요한 정보를 모은다 |
| 입력 | 해커톤 공지(주제·평가표), 멘토링 의견, 현재 제품 상태([C01](C01_프로젝트-한눈에.md)) |
| 하는 일 | 후보 비교(A/B/C), 팀 역량·시간 점검, 고객·수익 모델 정리, 사람 확인(실사용) |
| 산출물 | 선택한 방향 + 이유 → **C06 결정 기록**, D01 갱신 |
| ✅ 게이트 | ① 공식 주제·평가표를 확인했다 ② 만들 에이전트(1개 또는 2개)가 정해졌다 ③ 서버 도입 여부가 정해졌다 ④ 팀 전원이 방향을 설명할 수 있다 |

### G1. 설계 — 무엇을 만드는가

| 항목 | 내용 |
|---|---|
| 목적 | 시스템이 **무엇을 하고 누가 쓰는지**를 한 장으로 설명할 수 있게 한다 |
| 산출물 | **D01** 시스템 정의서, **D03** 사용사례(액터·주제) |
| ✅ 게이트 | ① D01만 읽고 비개발자가 "뭘 만드는지" 설명할 수 있다 ② 모든 액터와 주제(T-nn)가 D03에 있다 ③ **하지 않는 것**(범위 밖)이 적혀 있다 |

### G2. 스펙 — 정확히 무엇이 되어야 하는가

| 항목 | 내용 |
|---|---|
| 목적 | 만들 기능을 **검증 가능한 문장**으로 만든다 |
| 산출물 | **D04** 에픽·사용자 스토리(추정작업량·우선순위 포함) |
| 쓰는 법 | "(사용자)는 (목적)을 위하여 (행동)한다" + **완료 조건** 한 줄 ([§5](#5-스토리는-이렇게-쓴다)) |
| ✅ 게이트 | ① 모든 T-nn에 에픽이 있다 ② 모든 스토리가 **테스트할 수 있는 말**로 적혀 있다 ③ 우선순위(상·중·하)가 있다 ④ **R(리스크)** 이 D04 §3에 있다 |

### G3. 상세 설계 — 어떻게 만드는가 (화면·서버·데이터)

| 항목 | 내용 |
|---|---|
| 목적 | 개발자가 **막힘없이 구현**하고, 다른 사람이 **보고 이해**할 수 있게 한다 |
| 산출물 | D06 설계 부분(클래스·알고리즘·데이터·API·화면), 필요 시 C06 결정 |
| 꼭 정하는 것 | **프론트엔드**(화면·상태) / **백엔드·서버**(있으면 어떤 함수·경로) / **데이터**(어떤 키·모양·누가 쓰고 누가 읽나) / **연동**(외부 서비스·AI) / **실패했을 때**(폴백) |
| ✅ 게이트 | ① 데이터 계약(쓰는 쪽·읽는 쪽)이 표로 있다 ② API/인터페이스가 입력·출력·실패 시 동작까지 적혀 있다 ③ **넘지 않는 선**([C05 §2](C05_개발규칙.md))과 충돌하지 않음을 확인했다 ④ 테스트 방법이 정해져 있다 |

#### 상세 설계 체크리스트 (프론트 / 서버 / 데이터)

| 영역 | 질문 |
|---|---|
| **프론트엔드** | 어느 화면의 어느 부분이 바뀌나? 기존 화면 규칙(60px, 아이콘+글자+색, i18n)을 지키나? 실패 시 사용자는 무엇을 보나? |
| **서버/백엔드** | 어떤 경로(`/api/…`)? 입력·출력 형식? 키는 어디에? 느리거나 실패하면? 비용 상한은? |
| **데이터** | `Store` 어느 키를 쓰나? 모양을 바꾸나(바꾸면 읽는 화면 전부 확인)? 개인 식별 정보가 섞이지 않나? |
| **AI** | 어떤 단계가 AI이고 어떤 단계가 코드인가? 결과는 `waiting`으로만 들어가나? 사람은 어디서 승인하나? |
| **보안** | 비밀 값이 브라우저에 노출되나? AI 출력이 `innerHTML`로 들어가는 곳이 없나? |

### G4. 구현 — 스프린트로 쪼개 만든다

| 항목 | 내용 |
|---|---|
| 목적 | 작게 쪼개 **자주 확인**하며 만든다 |
| 입력 | D05 태스크 |
| 한 사이클 | **태스크 선택 → 브랜치 → 만들기 → 테스트 쓰기 → 망가뜨려 보기 → 전체 테스트 → 기록 → PR** ([C05 §6](C05_개발규칙.md)) |
| 산출물 | 코드, 테스트, 개발일지, D05 갱신 |
| ✅ 게이트 (태스크마다) | [§4 Definition of Done](#4-완료의-정의-definition-of-done) |
| ✅ 게이트 (스프린트 종료) | ① 계획한 스토리가 DoD를 통과했다 ② 전체 테스트가 통과한다 ③ D05 완료 표시와 D06 완료%가 맞다 ④ 다음 스프린트 계획 |

### G5. 검증·인계

| 항목 | 내용 |
|---|---|
| 목적 | **잘 되는지 증명**하고 발표·인계를 준비한다 |
| 산출물 | **D07** 시험결과서, **D08** 결과보고서, 시연 시나리오·영상, 발표 자료 |
| ✅ 게이트 | ① 기능 동결 후 D07 수행 결과가 채워졌다(예외 케이스 포함) ② 사람 확인 케이스를 실제로 수행했다 ③ 시연이 **실패해도** 진행되는 대비(녹화·수동 경로)가 있다 ④ D08의 모든 숫자에 근거 문서가 있다 |

## 4. 완료의 정의 (Definition of Done)

**태스크가 "끝났다"고 말하려면 아래를 모두 만족해야 한다.**

| # | 조건 | 확인 방법 |
|---|---|---|
| 1 | 스토리의 **완료 조건**이 눈으로 확인된다 | 화면에서 직접 시연 (`src/index.html` 더블클릭 → 예시 데이터) |
| 2 | **새 테스트**가 있다 (정상 + 비정상 케이스) | `tests/` |
| 3 | **일부러 망가뜨려** 테스트가 잡는 것을 봤다 | 개발일지에 한 줄 |
| 4 | **전체 테스트가 통과**한다 (기존 1,619건 포함) | `node tests/run-all.js` |
| 5 | **넘지 않는 선**을 어기지 않았다 | [C05 §2](C05_개발규칙.md) 체크 |
| 6 | **개발일지**에 적었다 (막혔던 것 / 어떻게 풀었는지) | `docs/devlog/` |
| 7 | **문서를 고쳤다** (D05 체크, 바뀐 명세는 D06) | [C03 §8](C03_문서체계와-ID규칙.md) |
| 8 | 배포가 필요한 변경이면 `sw.js` **VERSION**을 올렸다 | |
| 9 | PR 본문에 **무엇을·왜·어떻게 확인했나**를 적었다 | 비개발자가 읽을 수 있게 |

## 5. 스토리는 이렇게 쓴다

```
US-28  운영자는 번역 검수 시간을 줄이기 위하여, 한국어 안전 문구를 입력하면 AI가 6개 언어 번역과 역번역을 제안한다.
       완료 조건: (1) 번역이 'waiting' 상태로만 저장된다  (2) AI 호출이 실패하면 손으로 입력하는 칸이 그대로 있다
                  (3) 뜻이 뒤집힌 번역은 '사람에게 올림' 표시가 붙는다
       추정작업량: 8   우선순위: 상
```

| 좋은 스토리의 조건 (INVEST) | 풀이 |
|---|---|
| **독립적**이다 | 다른 스토리 없이도 만들 수 있다 |
| **협상 가능**하다 | 방법은 열려 있고 목적이 분명하다 |
| **가치**가 있다 | 누구에게 무엇이 좋아지는지 적혀 있다 |
| **추정 가능**하다 | 크기를 어림할 수 있다 (1·2·3·5·8) |
| **작다** | 8보다 크면 쪼갠다 |
| **테스트 가능**하다 | 완료 조건이 확인 가능한 문장이다 |

## 6. 스프린트 운영 (제안)

| 항목 | 내용 |
|---|---|
| 기간 | **2주 × 3회** (제안, 미확정 — [D05](../40_캡스톤산출물/D05_스프린트백로그.md)) |
| 시작 | 계획 회의 30분: 목표 한 줄 · 스토리 선택 · 태스크 쪼개기 · 담당 정하기 |
| 중간 | 짧은 점검(주 1~2회, 15분): 한 일 / 할 일 / 막힌 것 |
| 종료 | 확인 회의 30분: 시연 · DoD 확인 · 회고(좋았던 것 / 아쉬운 것 / 바꿀 것) |
| 개발자 1인일 때 | 용량을 **보수적으로** 잡는다. 지난 프로젝트에서 "4주가 사실상 2주"였다는 경험을 반영 → **계획의 절반만 확정, 나머지는 여유분** |
| 비개발 팀원 | 코드 밖의 태스크(현장 확인·조사·검토·발표)를 **같은 D05 표에** 넣고 같은 방식으로 관리한다 |

## 7. 변경이 생겼을 때 (예: 주제 공지 후 방향이 바뀜)

1. [C06](C06_결정기록.md)에 **새 결정**을 적는다 (옛 결정은 "대체됨")
2. G1부터 **영향받는 문서를 위에서 아래로** 고친다 (D03 → D04 → D05)
3. 이미 만든 코드가 있으면 **어디까지 재사용 가능한지** 먼저 표로 적는다
4. C01 상태판을 갱신한다
