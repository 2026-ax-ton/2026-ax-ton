# C09 · GitHub 사용법 — 코드를 몰라도 문서를 올리는 법

> **문서 상태** 초안 v0.1 (팀 검토 전) · **최종 수정** 2026-11-05 · **소유자** yesol (기획·디자인 팀, 작성 보조 Claude)
> **이 문서가 답하는 질문** GitHub는 우리 프로젝트에서 무엇을 하나 · 내 문서는 어디에 왜 들어가나 · 고친 내용과 버전을 어떻게 남기나 · 어떤 순서로 올리나 · 하면 안 되는 것은
> **대상** 개발자가 아닌 팀원. 이미 있는 규칙(`CLAUDE.md` git 절, `git-rules/GIT.md`, [C03](C03_문서체계와-ID규칙.md))을 **처음 읽는 사람 눈높이로 다시 풀어 쓴 것**이다. 규칙이 충돌하면 그 문서들이 먼저다.
> 조사일 2026-11-05. 저장소 설정은 `gh` 명령으로 읽어서 확인했고, 일반 설명은 GitHub 공식 문서를 근거로 했다 (끝의 출처).

## 1. 한 장 요약

- **GitHub = 파일의 변경 이력을 팀이 같이 쓰는 공유 폴더.** 누가 언제 무엇을 왜 바꿨는지가 전부 남는다.
- 우리 저장소: `https://github.com/2026-ax-ton/2026-ax-ton` — **공개(public)** 이다. 올린 것은 누구나 볼 수 있다.
- 흐름은 하나다: **내 브랜치에서 고친다 → PR(합치자는 요청)을 연다 → 확인받고 `develop`에 합친다.** 배포는 `main`만 하고 `main`은 byeonsoyun이 다룬다.
- 문서를 고칠 때마다 **문서 맨 아래 「제·개정 이력」에 한 줄** 쓰고, 커밋 메시지·PR 본문·`docs/devlog/yesol.md`에 같은 내용을 남긴다. (§6)

## 2. 용어 8개

| 말 | 뜻 | 비유 |
|---|---|---|
| 저장소 (repository) | 프로젝트의 모든 파일과 변경 이력이 든 곳 | 공유 드라이브 폴더 + 수정 기록 |
| 클론 (clone) | 저장소를 내 컴퓨터로 통째로 복사 | 공유 폴더를 내 PC에 내려받기 |
| 브랜치 (branch) | 원본을 건드리지 않는 내 작업 공간 | 문서의 「사본」을 만들어 거기서 고치기 |
| 커밋 (commit) | 고친 내용을 설명과 함께 한 번 저장 | 「저장 + 메모」. 되돌릴 수 있는 한 칸 |
| 푸시 (push) | 내 컴퓨터의 커밋을 GitHub로 올림 | 내 사본을 공유 드라이브에 올리기 |
| PR (pull request) | 「내 사본을 원본에 합쳐 주세요」라는 요청 + 토론 창 | 결재 올리기 |
| 리뷰 (review) | 팀원이 PR의 변경 내용을 읽고 의견을 남김 | 결재선 확인 |
| 머지 (merge) | 승인된 PR을 원본에 합침 | 결재 완료 후 원본에 반영 |

## 3. 우리 저장소 지도

### 3.1 브랜치 (표 1)

| 브랜치 | 역할 | 누가 | 이유 |
|---|---|---|---|
| `main` | **배포 전용.** 여기에 올라가면 운영 주소(Vercel)가 바뀐다 | byeonsoyun만 (배포 때 `develop`을 앞으로 감기) | GitHub 규칙 `main 보호`가 삭제·강제 덮어쓰기를 막고 PR을 요구한다. 코드가 바뀌지 않은 문서 커밋은 `main`에 올리지 않는다 (2026-08-30 결정) |
| `develop` | **기준 브랜치이자 GitHub 기본 브랜치.** 저장소 주소를 열면 이 브랜치가 보인다 | PR로만 합친다 | 최신 문서·코드가 모이는 곳. 배포 전에 쓰는 대기실 |
| `feature/<이름>-<주제>` | 내 작업 브랜치 (예: `feature/yesol-docs`, 팀원 `feature/Subin-prd`) | 각자 | 합치기 전에는 아무도 영향받지 않는다 |
| `feat/agent-*` | 개발자의 해커톤 기능 작업 | byeonsoyun | |

> **`feature/yesool`(이름 끝이 `yesool`)은 쓰지 않는다.** 옛 Next.js+Supabase 프로젝트가 들어 있고 지금 저장소와 **공통 조상이 없다.** 그 이름으로 작업하면 무관한 이력이 통째로 섞인다. 지우지도 않는다 (`CLAUDE.md`가 보존하기로 정했다).

`develop`에는 보호 규칙이 없어서 기술적으로는 바로 올릴 수 있다. **그래도 올리지 않는다** — PR 기록이 「어떻게 만들었나」의 증거(심사)이고, 실수를 PR 단계에서 잡는다.

### 3.2 자동으로 돌아가는 것

- **전체 검사 (CI):** PR을 열면 `.github/workflows/test.yml`이 자동 테스트를 돌린다. PR 화면 아래쪽 **초록 ✓**면 통과, **빨간 ✗**면 클릭해서 이유를 본다. 지금은 통과가 머지의 필수 조건은 아니지만 ✗를 두고 합치지 않는다.
- **Vercel 미리보기:** PR마다 Vercel이 임시 주소를 만들어 PR 댓글에 올린다. **화면을 바꾸지 않은 문서 PR에서도 만들어진다.** 화면 변경은 이 주소를 눌러 눈으로 확인한다.

### 3.3 폴더 — 내 파일은 어디로, 왜 (표 2)

C03 §2.4-B의 원칙을 내 파일 기준으로 다시 정리했다.

| 만드는 것 | 들어가는 곳 | 이름 규칙 | 왜 거기인가 |
|---|---|---|---|
| 제품 정의·PRD 검토·벤치마킹 | `docs/documentations/30_제품정의/` | `P{두 자리}_한글이름.md` | PRD가 있는 폴더라서 같은 사슬(「왜·무엇」)에 붙는다 |
| 규칙·사용법 (이 문서) | `docs/documentations/00_개발컨벤션/` | `C{두 자리}_한글이름.md` | 팀이 따를 규칙·절차 |
| 사업화(수익·숫자·사업계획) | `docs/documentations/10_사업화/` | `S{두 자리}_….md` | 숫자 출처는 S02 먼저 (C03 §8) |
| 기술 명세 | `docs/documentations/20_기술명세/` | `A…`·`SPEC-…` | 기술은 한 폴더 |
| 멘토링 회차 자료 | `docs/infos/05_멘토링/<날짜_종류>/` | ID 그대로 | 회차별 원본 |
| 발표 자료 | `docs/발표/<연월_대회>/` | | |
| 내 작업 기록 | `docs/devlog/<이름>.md` | 사람마다 파일 1개 | 같은 파일을 여럿이 고치면 충돌나서 사람별로 나눴다 |
| 안 쓰는 문서 | `docs/documentations/90_보관/` | | 지우지 않고 치워 둔다 |
| 코드·테스트가 경로를 직접 보는 것 (`docs/00~12`, `CLAUDE.md`, `tests/`, `src/`, `api/`) | **옮기지 않는다** | | 테스트·개발 루틴이 경로에 묶여 있다 |

- 같은 내용은 **한 곳에만** 쓴다 (C03 §3). 이미 있는 내용은 복사하지 말고 링크한다.
- 숫자에는 **출처와 측정일**, 추측은 「추측」이라고 표시한다 (C03 §6). 발표용 숫자는 **S02 수치 근거 대장**에 먼저 올린다.
- **개인정보·키·비밀번호·인터뷰 대상자의 실명은 올리지 않는다.** 저장소가 공개라 한 번 올라가면 이력에 영원히 남는다.

## 4. 내 작업 흐름

기본 방식: **Claude가 명령을 대신 실행하고, push 전에 반드시 내게 묻는다.** 나는 PR 화면에서 변경 내용·CI ✓·미리보기를 읽고 확인한다. (`CLAUDE.md`는 「사용자 대신 당신이 git을 실행한다」고 정하고 있다. 다만 **삭제·브랜치 변경·되돌리기 어려운 일은 먼저 묻는다.**)

### 4.A 파일 한 줄만 고칠 때 — 웹에서

1. GitHub에서 파일을 연다 → 오른쪽 위 **연필 아이콘**.
2. 고친다.
3. **Commit changes…** → 메시지 쓰기 → **「Create a new branch for this commit and start a pull request」** 선택 (기본 브랜치 `develop`에 바로 커밋하지 않는다).
4. 열린 PR 화면에서 §5의 본문을 쓰고 **Create pull request** (base가 `develop`인지 확인).

### 4.B 여러 파일을 만들 때 — 내 컴퓨터에서

한 번만:
```bash
gh repo clone 2026-ax-ton/2026-ax-ton   # 또는 git clone https://github.com/2026-ax-ton/2026-ax-ton.git
cd 2026-ax-ton
git config user.name  "내 이름"
git config user.email "내 GitHub noreply 주소"   # 개인 이메일이 공개 커밋에 남지 않게. 주소는 GitHub 설정 > Emails 에 있다
```
작업할 때마다:
```bash
git switch develop && git pull origin develop      # 1. 최신으로 맞춘다 (매일 시작할 때)
git switch -c feature/<이름>-<주제>                 # 2. 내 브랜치를 새로 딴다 (이미 있으면 git switch 만)
# ... 파일을 만들고 고친다 ...
git status                                          # 3. 무엇이 바뀌었는지 본다
git add <고친 파일 경로>                            # 4. 고친 파일만 고른다. `git add .` 는 쓰지 않는다
git commit -m "docs: 한국어 설명 (문서 ID · 버전)"   # 5. 한 가지 변경에 한 커밋
git push -u origin feature/<이름>-<주제>            # 6. 처음 올릴 때 (이후에는 git push)
gh pr create --base develop --draft                 # 7. 초안 PR 열기 (또는 GitHub 웹의 「Compare & pull request」)
```
- `git add .`를 쓰지 않는 이유: 의도하지 않은 파일(임시 파일, 개인 파일)이 같이 올라간다. 무엇을 고쳤는지가 커밋에 그대로 남아야 나중에 되짚을 수 있다.
- PR이 **초안(draft)** 이면 「아직 작성 중」이라는 뜻이다. CI ✓와 미리보기를 확인한 뒤 **Ready for review**로 바꾸고 리뷰어를 지정한다.
- PR이 머지된 뒤: `git switch develop && git pull origin develop`로 내 컴퓨터를 맞춘다. 내 브랜치는 PR 화면의 **Delete branch**로 지울 수 있다 (선택).

### 4.C 합치는 사람

지금 관행은 PR을 연 사람이 직접 합치고 리뷰는 없었다(PR #1~#3). 규칙(`git-rules/GIT.md`)은 「팀원 승인 후 합친다」이다. 우리 문서 PR은 **리뷰어로 byeonsoyun을 지정하고 승인(또는 「확인했다」 댓글)을 받은 뒤** 합친다. 내가 올린 PR을 내가 합치는 것은 확인을 받은 뒤에만 한다.

## 5. 커밋 메시지와 PR 본문

### 5.1 커밋 메시지 (팀 관례)

`접두사: 한국어 설명 (문서 ID · 버전)` — 접두사는 이 중 하나.

| 접두사 | 언제 | 예 |
|---|---|---|
| `docs:` | 문서를 만들거나 고쳤다 (우리 대부분) | `docs: P02 타사 앱 벤치마킹 v0.1 추가` |
| `feat:` | 기능 추가 (코드) | |
| `fix:` | 오류 수정 | |
| `chore:` | 설정·정리 | |

- 한 커밋에는 **독립적이고 완결된 변경 하나**만 담는다. 문서 두 개를 고쳤어도 서로 상관없으면 커밋을 둘로 나눈다 (한쪽만 되돌리기 쉽다).
- 메시지는 구체적으로: `fix typo`처럼 무엇인지 알 수 있어야 한다.

### 5.2 PR 제목과 본문 (팀 관례 + GitHub 권고)

제목은 커밋과 같은 형식. 본문은 아래 틀을 그대로 복사해서 쓴다.

```markdown
## 무엇을 했나
- (한 문장 요약, 바뀐 파일과 버전 표)

| 문서 | 이전 | 이후 | 바뀐 점 |
|---|---|---|---|

## 왜
- (어떤 결정·요청·문제 때문인지. 관계된 C06 결정 번호, PR, 회의)

## 어떻게 확인했나
- (CI ✓ / 링크 점검 / 숫자 출처 대조 / Vercel 미리보기)

## 남은 것 · 확인 부탁
- (리뷰어에게 묻는 것, 아직 못 한 것)
```

- 이슈 번호가 있으면 본문에 `Closes #번호`. 기본 브랜치가 `develop`이라 `develop`으로 가는 PR에서 동작한다. (지금은 이슈를 쓰지 않는다. 할 일은 [C01 §7](C01_프로젝트-한눈에.md)에 있다.)
- 리뷰어가 읽는 것은 PR 본문이다. 코드를 모르는 팀원도 읽을 수 있게 쓴다.

## 6. 변경사항과 버전을 남기는 법

**문서를 고칠 때마다 이 순서로 한다** ([C03 §8](C03_문서체계와-ID규칙.md)): ① 내용 수정 → ② 문서 맨 아래 `제·개정 이력`에 한 줄 → ③ 영향받는 문서 확인 → ④ [C01](C01_프로젝트-한눈에.md) 상태판 갱신(필요할 때).

### 6.1 버전 올리는 규칙 ([C03 §4.3](C03_문서체계와-ID규칙.md))

| 바뀐 것 | 버전 | 예 |
|---|---|---|
| 오타·표현 다듬기 | 올리지 않음 (이력도 생략 가능) | |
| 내용 추가·수정 | **부** +1 | 1.0 → 1.1 |
| 구조·범위가 바뀜 (기능 추가·삭제) | **주** +1 | 1.x → 2.0 |
| 검토 전 초안 | 0.x | 0.1 → 0.2 |

### 6.2 한 번의 변경이 남기는 곳 4군데

| 어디 | 무엇을 쓰나 | 왜 |
|---|---|---|
| 문서의 `제·개정 이력` 표 | `\| 버전 \| 날짜 \| 작성자 \| 제/개정사항 \| 비고 \|` 한 줄 | 문서만 열어도 어떻게 변했는지 안다 |
| 커밋 메시지 | `docs: … (문서 ID · 버전)` | `git log`로 되짚는다 |
| PR 본문 | 문서·이전/이후 버전 표, 왜, 확인 | 리뷰어가 읽는다. 심사에서 「어떻게 만들었나」의 증거 |
| `docs/devlog/yesol.md` | 날짜 · 한 것 · 막힌 것 · 다음에 할 것 (새 날짜를 위에 쌓는다) | 내 변경 기록. 같은 일이 반복될 때 푼 방법을 다시 찾는다 |

### 6.3 GitHub 자체의 버전 표시

- **태그·릴리스**는 「이 시점의 저장소 전체」에 이름을 붙이는 것이다 (예: `v1.0-ideathon`). 배포를 맡은 byeonsoyun이 정한다. 우리 문서는 위 4군데로 충분하다.
- 어떤 줄이 언제 누구에 의해 바뀌었는지는 GitHub 파일 화면의 **History**(변경 이력)와 **Blame**(줄별 작성자)으로 볼 수 있다.

## 7. 하면 안 되는 것

| 하지 않는다 | 이유 |
|---|---|
| `main`·`develop`에 직접 push | `main`은 배포가 바뀐다. `develop`은 PR 기록이 증거라서 |
| `git push --force`, `git reset --hard` | 남의 변경까지 지워질 수 있다 (`CLAUDE.md`가 금지) |
| `git add .` | 의도하지 않은 파일이 올라간다. 파일 경로를 지정한다 |
| `feature/yesool` 브랜치·옛 클론에서 작업 | 공통 조상이 없는 다른 프로젝트다 (§3.1) |
| 개인정보·키·실명·큰 파일을 올림 | 공개 저장소. 올리면 이력에 남는다 |
| 코드·테스트가 보는 경로의 파일을 옮김 | 테스트가 깨진다 (§3.3 마지막 줄) |
| 같은 내용을 두 곳에 복사 | 한쪽만 고쳐져 어긋난다 (C03 §3). 링크한다 |
| CI ✗ 상태로 합침 | 문서도 링크 점검 등이 걸릴 수 있다 |

## 8. 막혔을 때

- **충돌(conflict)**: 같은 파일의 같은 줄을 둘이 고쳤다는 뜻이다. 파일에 `<<<<<<<` `=======` `>>>>>>>`가 생긴다. 혼자 판단하지 말고 Claude에게 상황을 말한다. VS Code에서는 **Accept Current Change**(내 것) / **Accept Incoming Change**(팀원 것) / 둘 다 중 고른 뒤 `git add <파일>` → `git commit`. 색인 표(README의 문서 목록 줄)가 가장 많이 충돌한다.
- **아직 커밋하지 않은 수정을 버리고 싶을 때**: `git restore <파일>` — **되돌릴 수 없으니 버려도 되는지 확인하고** 실행한다.
- **이미 올린 커밋을 취소하고 싶을 때**: 지우지 말고 `git revert <커밋>`(취소하는 새 커밋을 만든다).
- **브랜치를 잘못 만들었을 때**: `git switch develop`로 돌아가 새 브랜치를 딴다. 고쳐 둔 파일은 `git stash`로 잠시 치워 둘 수 있다.
- **모르겠을 때**: 아무것도 지우거나 덮어쓰지 말고 byeonsoyun에게 PR 댓글로 묻는다. 규칙: 모르는 것은 모른다고 쓰고 **「미정 (담당·기한)」** 으로 적는다 ([C07](C07_역할과-운영.md) 소통 규칙).

## 9. 첫 연습 — 작은 PR 하나

1. `git switch develop && git pull origin develop`
2. `git switch -c feature/<이름>-docs`
3. 문서 한 곳을 고친다 (예: 이 문서의 이력에 한 줄)
4. `git status` → `git add <그 파일>` → `git commit -m "docs: … "`
5. `git push -u origin <브랜치>` → `gh pr create --base develop --draft`
6. PR 화면에서 **변경 파일**, **CI ✓**, **Vercel 미리보기**를 눈으로 확인한다.
7. Ready for review → 리뷰어 지정 → 승인 뒤 머지 → `git switch develop && git pull origin develop`.
