# C06 · 결정 기록 (ADR)

> **문서 상태** 초안 v0.1 · **최종 수정** 2026-10-10
> **이 문서가 답하는 질문** "이건 **왜 이렇게** 하기로 했지?" · "**누가 언제** 정했지?" · "**바꾸려면** 어떻게 하지?"
> ADR = Architecture Decision Record (결정 기록). 큰 결정마다 한 건씩, **결정과 이유와 대안**을 남긴다.

## 1. 쓰는 법

| 규칙 | 내용 |
|---|---|
| 언제 쓰나 | 나중에 "왜?"라고 물을 만한 결정, 되돌리기 비싼 결정, 팀 의견이 갈린 결정 |
| 상태 | **확정** · **후보** · **제안** · **미정** · **대체됨**([C03 §5](C03_문서체계와-ID규칙.md)) |

| 확정 조건 | 후보를 **확정**으로 올릴 때는 날짜와 결정자를 적는다 |

## 3. 결정 상세

### D-001 · 새로 만들지 않고 이어간다 — 확정

| | |
|---|---|
| **배경** | 아이디어톤에서 화면 11개·테스트·배포까지 완료. 해커톤은 약 6주. |
| **선택지** | (a) 새 주제로 처음부터 (b) 기존 제품 위에 AI Agent 추가 |
| **결정** | (b) |
| **이유** | ① 같은 완성도를 다시 만들면 그것만으로 기간이 다 간다 ② 아이디어톤 때 이미 "다음 단계" 로드맵이 있었다 ③ 아이디어톤 자체 평가의 **가장 약한 칸**("AI가 실제로 안 돈다")이 해커톤 평가표(AI 활용 20점)와 정확히 맞는다 |
| **영향** | 기존 11개 화면·테스트 1,619건을 **계속 통과**시켜야 한다 |
| **되돌리는 조건** | 해커톤 공식 주제가 현재 제품과 맞지 않을 때 |

### D-002 · 노동자 화면 0건, 관리자 화면만 AI — 확정

| | |
|---|---|
| **배경** | 규칙 "외부 요청 0건"과 "AI API 호출"이 정면으로 충돌한다 |
| **선택지** | ① 화면 구분 없이 서버리스 예외 하나 ② **노동자 화면은 0건 유지, 관리자·운영자 화면만 AI 허용(③)** ③ 빌드 시점에 번역을 정적 파일로 생성 |
| **결정** | ② |
| **이유** | 현장 인터넷이 약하다는 전제와 오프라인 동작이 노동자 쪽에 걸려 있다. 관리자는 인터넷이 있는 사무실에서 쓴다. ①은 오프라인 전제를 무너뜨리고, ③은 운영자가 새 문구를 넣는 순간 쓸 수 없다. |
| **영향** | 에이전트 결과는 `Store` 데이터로만 노동자에게 도착한다. AI 실패 시 손으로 하던 길이 남는다. |
| **출처** | `docs/12-hackathon-agent-plan.md` §2 |

### D-003 · 공지 전에는 에이전트 코드 안 쓴다 — 확정

| | |
|---|---|
| **이유** | 주제가 "현장 안전"이냐 "다국어"냐 "데이터 분석"이냐에 따라 만들 에이전트가 달라진다. 지금 쓰면 다시 쓴다. |
| **대신 하는 것** | 문서 체계, 사람 확인(실사용), 수익 모델, 출처 검증, 기반 설계 |
| **풀리는 조건** | 공식 주제·평가표 공지 |

### D-005 · 서버리스 함수 경유 — 후보

| | |
|---|---|
| **배경** | AI 키를 `src/`에 두면 배포 주소를 여는 누구나 가져간다. 프로젝트에 **처음 생기는 서버 코드**가 된다. |
| **선택지** | ① Vercel 서버리스 함수 `/api/*` ② 별도 백엔드 서버 신설 ③ AI 호출 없이 미리 만든 결과를 보여 주는 시연 방식 |
| **제안** | ① (서버를 직접 운영하지 않고 지금 배포 환경을 그대로 활용) |
| **걸림** | Vercel **Root Directory**(지금 `src`)가 바뀔 수 있음 → 배포 설정 변경이므로 **소유자 승인 필요**. 바꾼 뒤에는 `docs/`·`tests/`가 여전히 404인지 **다시 확인**해야 한다. |
| **영향** | `/api`만 의존성을 가진다. `src/`는 계속 의존성 0. |
| **결정 필요** | 멘토 의견(Q10) + 소유자 승인 |

### D-006 · 에이전트 루프를 어디서 돌리나 — 후보

| | A. 브라우저가 단계를 지휘 | B. 서버 함수 안에서 전체 루프 |
|---|---|---|
| 방식 | 서버 함수는 "번역 1회", "역번역 1회"처럼 **한 단계만** 한다. 재시도·비교는 화면 쪽 코드가 한다. | 서버 함수 한 번 호출에 번역→역번역→비교→재시도를 **전부** 한다. |
| 비교 도구 `review.js` | **기존 코드를 그대로 재사용** (한 곳에서 관리) | 서버에서도 쓰려면 **복사하거나 구조를 바꿔야** 한다 (두 곳 → 어긋날 위험) |
| 진행 표시 | 단계마다 화면에 보여 줄 수 있다 (시연에 유리) | 한 번에 오래 걸리면 서버 시간 제한에 걸릴 수 있다 |
| 키 보호 | 안전 (키는 서버 함수에만) | 안전 |
| 단점 | 관리자가 창을 닫으면 루프가 멈춘다 | 서버 코드가 늘고 테스트 환경이 복잡해진다 |
| **제안** | **A** (재사용·시연·단순함) | |

멘토에게 묻는다: **Q5, Q7** (`MENTORING-QUESTIONS.md`).

### D-007 · 에이전트 개수 — 제안

하나를 끝까지 동작하는 시연으로 만들고, 나머지는 설계(로드맵 슬라이드)로 둔다. 근거: 개발자가 사실상 1명이고, 과거 프로젝트에서 "4주가 사실상 2주"였다. 평가표의 "구현·확장"은 설계 문서로도 일부 설명된다. **공지 후 재검토.**

### D-008 · 문서 체계 도입 — 확정(체계) / 미정(제출)

- 확정: C 문서(약속집)와 D01~D08을 프로토타입으로 만들고 비개발 팀원 피드백으로 개선한다.
- **미정**: D01~D08 양식은 **캡스톤 산출물 양식**(`2025-개정-D01~D08` hwp)에서 가져왔다. 해커톤 제출 요구인지는 확인하지 못했다. 담당: byeonsoyun, 확인 시점: 공지 후.
- 어느 쪽이든 문서 체계는 "지금 무엇을 하는지 이해하기 어렵다"는 문제를 줄이는 데 쓴다.

### D-009 · 이주노동자 데이터 판매 — 제안: 채택하지 않음

| | |
|---|---|
| **출처** | 멘토링 1차(2026-10-10) 아이디어: "이주 노동자 관련 데이터를 수집해서 파는 건?" |
| **충돌하는 우리 원칙** | P-3 익명 제보 보호 · P-5 인사평가용 내보내기 금지 · P-8 식별번호 미수집. 개인정보 보호 관점에서 노동자 개인 데이터를 판매하는 모델은 제품 전제(감시 도구가 되면 현장이 등을 돌린다)와 맞지 않는다. |
| **대안으로 검토할 수 있는 것** | **익명·집계된** 교육 효과 통계를 기관에 제공하는 구독형 리포트 (개인 식별 불가). 법적 검토가 필요하므로 `미정`. |
| **다음** | 팀이 채택 여부 확인. 기록은 남긴다. |

### D-010 · 고객·수익 모델 B2G 중심 — 제안

멘토 의견 요약: 실제 사용자(이주노동자)에게서는 돈이 나올 수 없다. 돈을 쓸 사람은 **기관·공무원, 정부·지자체**, 그리고 증빙이 필요한 **사업주**다. 수익 모델과 가격 정책, 추정 수익은 발표에 필요하다.
정리할 것: 고객 유형별(사업주·기관·지자체·산업안전 관련 단체) **누가 왜 돈을 내는가 / 얼마나 / 무엇을 받는가**. 숫자는 **출처가 확인된 것만** 쓰고, 추정은 추정이라고 표시한다 ([C03 §6](C03_문서체계와-ID규칙.md) 7·8번). 담당: `미정`.
