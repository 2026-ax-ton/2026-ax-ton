## 2. 개발 프로세스

### 2.1 프로세스 모형
**점진적 모델(Incremental Model) + 2주 스프린트**를 채택한다.

- 채택 근거:
  - 아이디어톤 판(v1.0)이 이미 동작한다. 해커톤 버전은 그 위에 **AI 에이전트라는 증분 하나**를 얹는다 ([C06 D-001](../00_개발컨벤션/C06_결정기록.md)).
  - 요구가 바뀌는 시점이 정해져 있다 — 운영 공지(평가표 10/23), 멘토링 6회. 계획 전체를 먼저 고정하는 방식은 맞지 않는다.
  - 개발자가 1명이다. 작은 단위로 끝내고 테스트로 고정해야 위험을 일찍 본다.
- 단, **설계 문서는 구현 전에 끝낸다** — 기술 멘토 6단계(역할 → 범위 → 기능 정의 → PRD → Spec → CodeGen)를 따른다 ([P00](../30_제품정의/P00_제품정의-작업흐름.md)).

### 2.2 개발 절차

```
 G0 방향 확인 → G1 설계 → G2 스펙 → G3 상세 설계 → G4 구현(스프린트) → G5 검증·인계
  (공지·멘토링)   D01·D03    D04·PRD   SPEC·A02·D06    D05 → 코드·테스트    D07·D08·시연
```

그림 1. 개발 절차 (단계별 통과 조건은 [C04](../00_개발컨벤션/C04_개발순서와-게이트.md))

실제 운영 절차:
`태스크 선택(07-next-tasks H절·D05) → 작업 브랜치 feat/agent-* → PRD §4·SPEC 읽기 → 구현 → 테스트 추가 → 일부러 망가뜨려 확인 → 전체 테스트 → 개발일지 → PR → develop 머지 → (배포 시) main --ff-only`

> 🔑 이 프로젝트의 특징: **제품 원칙을 테스트가 지킨다.** 익명 신고·검수된 문구만·외부 요청 0건·"면책" 없음이 코드에 남아 있는지 자동 테스트가 매번 본다. AI 에이전트도 같은 방식으로 **가짜 응답 경계 테스트**로 선을 고정한다.

### 4.2 Ground Rules

1. **결정은 글로 남긴다** — 말로 정한 것은 [C06](../00_개발컨벤션/C06_결정기록.md)에 24시간 안에 적는다.
2. **모르면 `미정` + 담당 + 기한** — 빈칸을 두지 않는다.
3. **AI는 초안까지, 승인은 사람** — 안전 지시가 되는 모든 문장은 사람이 승인한다.
4. **`main`에 작업 커밋을 직접 올리지 않는다** — `feat/agent-*` → PR → `develop` → (배포) `main --ff-only`.
5. **전체 테스트가 통과한 채로만 머지한다** (기준 1,619건 + 새 테스트).
6. **코드 밖의 일도 같은 표에서 관리한다** — 인터뷰·검증·발표도 D05 태스크로 적는다.
7. **숫자에는 출처와 측정일** — [S02](../10_사업화/S02_수치-근거대장.md)에 없는 숫자는 쓰지 않는다.
8. **피드백 기한이 지나면 안대로 확정한다** (D-022 제안).
