## 1. 프로젝트 개요

### 1.1 시스템 명칭

이주노동자 안전교육 이해도 검증 플랫폼 (가칭 · **제안**)

### 1.2 시스템 개요

→ [D01](D01_시스템정의서.md) 참조.
한 줄 요약: 외국인 노동자가 안전교육을 이해했는지를 내 언어 음성과 그림 문제로 확인하고, 그 결과를 증빙으로 남기는 웹 서비스. 해커톤 버전은 여기에 AI 에이전트(번역·검수 등, **후보**)를 더한다.

## 2. 개발 프로세스

### 2.1 프로세스 모형

- 채택한 모형 : **애자일 스크럼 (소규모 변형)** — 2주 스프린트 × 3회 (**제안**)
- 채택 근거 :
  - 해커톤 주제·평가표가 공지되면 요구가 바뀔 수 있어, 계획 전체를 먼저 확정하는 방식(폭포수)은 맞지 않는다.
  - 팀이 4명이고 개발 가능 인원이 1명이라, 작은 단위로 자주 확인해야 위험을 일찍 발견한다.
  - 기존 제품(v1.0)이 완성되어 있어, 증분을 얹는 방식이 적합하다.
  - 단, **설계·스펙 문서는 구현 전에 쓴다** (설계 → 스펙 → 상세 설계 → 개발 순서, [C04](00_개발컨벤션/C04_개발순서와-게이트.md)).

### 2.2 개발 절차

```
 G0 방향 확인 → G1 설계 → G2 스펙 → G3 상세 설계 → G4 구현(스프린트 ×3) → G5 검증·인계
  (공지 확인)   D01·D03    D04      D06 설계안     D05 → 코드·테스트      D07·D08·시연
```

그림 1. 개발 절차 (단계별 통과 조건은 [C04](00_개발컨벤션/C04_개발순서와-게이트.md))

실제 운영 절차 : 태스크 선택 → 작업 브랜치(`feat/agent-*`) → 작게 구현 → 테스트 작성 → 일부러 망가뜨려 확인 → 전체 테스트 → 개발일지 → PR → `develop` 머지 → (배포 시) `main` `--ff-only`.

## 4. 프로젝트 운영 관리

### 4.1 팀 미팅 계획

**(1) 정기 회의**
- 시간 : 주 1회, 요일·시각 `미정` (30~40분) — 담당 byeonsoyun, 1차 스프린트 시작 전 확정
- 토의 내용 : 지난주 한 일 / 이번 주 할 일 / 막힌 것 / 상태판([C01](00_개발컨벤션/C01_프로젝트-한눈에.md)) 갱신
- 참석자 : 팀원 전원

**(2) 비정기 회의**
- 결정이 필요하거나 막힌 일이 생길 때 소집한다 (메신저 5분 점검 포함). 해커톤 공지 직후에는 방향 결정 회의를 연다 (G0).

**(3) 프로젝트 발표 미팅**
- 멘토링(온라인, 10월)·오프라인 해커톤(11월 말, 서울)에 맞춰 일정을 잡는다. 날짜 `미정` (공지 후 기입).
- 발표 리허설은 3차 스프린트에 최소 2회 한다. (**제안**)

### 4.2 Ground Rules

1. **결정은 글로 남긴다** — 말로 정한 것은 [C06 결정 기록](00_개발컨벤션/C06_결정기록.md) 또는 회의 메모에 24시간 안에 적는다.
2. **모르면 `미정`+담당+기한으로 쓴다** — 빈칸을 두지 않는다.
3. **AI는 초안·제안까지, 승인은 사람** — 안전 지시가 되는 모든 문장은 사람이 승인한다.
4. **`main`에 직접 작업 커밋을 올리지 않는다** — 작업 브랜치 → PR → `develop` ([C05 §5](00_개발컨벤션/C05_개발규칙.md)).
5. **전체 테스트가 통과한 채로만 머지한다** (기존 1,619건 포함).
6. **코드 밖의 일도 같은 표에서 관리한다** — 조사·인터뷰·검증·발표도 D05 태스크로 적는다.
7. **숫자에는 출처와 측정일을 붙인다** — 출처 없는 수치는 문서와 발표에 쓰지 않는다.
